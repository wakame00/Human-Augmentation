# Gemini 現状整理レビュー（2026-07-28）

## 依頼内容

Human Augmentation の実装済み、部分実装、未実装、技術的リスク、次の優先順位の整理。

## Geminiの応答状況

- 1回目: `gemini-3.1-flash-lite` はリポジトリを参照せず、中国語で一般的な人体改造Mod案を回答した。
- 2回目: `gemini-3.1-flash-lite` は HTTP 503。ランチャーが `gemini-3.5-flash-lite` へフォールバックした。
- フォールバック後も日本語指定を無視して中国語で回答し、プロンプトに記載した実装済み機能の一部を今後の工程として扱った。

このため、Gemini回答は現在の実装状況を示す一次資料としては採用しない。

## 採用できる提案

1. 人体改造パーツをデータ駆動化する。
   - 将来、性能、消費、ティア、適合部位をJSONへ移す案として有効。
   - 現時点ではJavaクラスと登録IDに効果が固定されているため、T3以降の種類が増える前に検討する。

2. 外部Mod連携をソフト依存として隔離する。
   - `ModList`、条件付きレシピ、隔離されたcompatパッケージを使う方針は既存設計と一致する。
   - 外部APIを本体の常時ロードされるクラスへ漏らさない。

3. 大規模機能を段階的に実装する。
   - 基礎人体・手術、耐久と修理、DNA能力、T3-T5、外部連携の順に分割する考え方は妥当。

## 誤り・不採用

- Attachment、T1/T2パーツ、300x244 UI、3x4x3手術設備は既に実装済みであり、今後のPhase 1/2/4ではない。
- Geminiが例示した11部位（耳、肝臓など）は実際の `BodySlot` と一致しない。
- 100/85/50/0は人工パーツの耐久出力率であり、人間性や排異反応の閾値ではない。
- 「サイバー精神病」「幻覚」「常時義体電力」は現在の合意仕様ではない。
- Createの回転力からFE/SPへの直接変換、Mekanismケーブル充電、Blood Magic LP駆動は未設計であり、実装済みとして扱わない。
- 外部Mod APIは `ModList.isLoaded` だけでは安全にならない。外部型を参照するクラスのロード隔離とバージョン・登録ID検証が必要。
- Gemini提示コードは現在のNeoForge登録コードとして検証されていないため、そのまま使用しない。

## Codexによる結論

次の優先順位を推奨する。

1. 手足UI試作から正式配置を決定する。
2. 人工パーツ修理を実装し、耐久システムのゲームループを完成させる。
3. 固定最大枠＋サーバー設定によるティア別使用可能スロット数を実装する。
4. 腕・脚パーツの性能計算と損傷対象を詳細化する。
5. DNA能力発現を少数のバニラMobから実装する。
6. T3設備とパーツを追加する。
7. 大型コントローラ式マルチブロックへ進む。
8. Create導入環境で既存の任意連携試作を検証してから連携範囲を拡張する。
